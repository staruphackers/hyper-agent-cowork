# v2026.1014.0-zhtw.11

**類型**：功能＋修正版（介面內一鍵登入）　**基於**：v2026.1003.0-zhtw.10　**建版目標**：`main`

## 摘要

在 Docker／VPS 上跑 Paperclip 時，Grok 與 Codex 訂閱登入不用再進主機終端機：按下登入後，伺服器自己在背景執行裝置碼登入，畫面直接顯示授權按鈕與驗證碼，在瀏覽器按允許就完成。同時修掉 2026-10-14 實際事故的整條鏈：登入檔變成 root 讀不到、每登入一次就多一條連線、新登入不會變成預設、舊連線失效時測試按鈕只顯示「Internal server error」、Grok 連線看不出是哪個帳號。

## 變更

### 新增
- **介面內裝置碼登入（Grok／Codex）**：本機環境的「本機登入」改由伺服器以執行 Paperclip 的同一個使用者身分執行 `grok login --device-auth`／`codex login --device-auth`，畫面分兩步：①「前往 x.ai／OpenAI 授權」（同時把驗證碼複製到剪貼簿）②驗證碼（OpenAI 要在授權頁輸入；Grok 確認與授權頁顯示的相同再按允許）。授權後自動偵測，不用回終端機。原本的終端機指令收進預設收合的「進階：改用終端機登入」。
- 登入程序的生命週期由伺服器管理：取消、完成、重新開始、逾時、伺服器關閉都會整組終止；程序意外結束時自動重啟一次；全伺服器同時登入上限 20。
- 登入程序只拿到登入需要的環境變數（PATH、語系、時區、暫存目錄、proxy／憑證設定），伺服器的資料庫連線、auth secret、`PAPERCLIP_*` 等一律不傳。

### 修正
- **同一帳號重新登入就更新原連線**：個人 Grok／Codex 訂閱以帳號 email 判斷，同帳號不再新增重複連線；這次選的代理人會補裝上去（不移除既有安裝）。
- **新登入何時成為預設**：只在「還沒有預設」「原預設已失效或不可用」「這次重新登入的就是原預設」時才換；取代失效預設時，會把新連線補裝到原預設的安裝對象，原本用預設的代理人不會被擋。健康的 API 金鑰預設不會被訂閱登入搶走。
- **登入失效不再 500**：Grok CLI 在 token 無法更新時會刪掉登入檔，舊版清理流程讀不到檔就整個 500。現在改成把該連線標為「登入已失效」，帳號頁顯示醒目的「重新登入」按鈕；若執行期間剛重新登入過，不會誤標。
- **Grok 連線顯示帳號 email**（原本永遠空白，三條同名「My Grok subscription」無從分辨）。
- 隱式同帳號更新前會再次確認授權仍有效，不會把剛撤銷的帳號救活。
- 複製驗證碼被瀏覽器拒絕時會明說，請使用者手動複製。

### 繁中用語
- 「Make default」由「建立預設」更正為「設為預設」；「Your default」→「目前預設」；帳號／應用程式相關的「Connect」統一為「連線」；「代碼」統一為「驗證碼」；新增裝置碼登入與登入失效相關文案 14 條。

### 已知限制
- 既有的舊連線不會自動合併：舊版存的 Grok 連線沒有帳號 email，新登入會另外新增一條。升級後請把新登入那條設為預設（或先移除舊的重複連線），見「升級注意」。
- 明示「重新連線」不會改動安裝對象（重新連線流程沒有選代理人的步驟，避免把個人連線裝到全公司）。
- 登入程序表只存在單一伺服器的記憶體中（目前正式站為單一實例）。

### 測試
- 每項修正都有測試並做過反向對照。新增測試檔：`server/src/__tests__/local-ai-device-login.test.ts`、`server/src/__tests__/ai-connections-same-account.test.ts`、`ui/src/components/ai-connections/AiConnectionAccountControls.test.tsx`；擴充 `useLocalAiLogin.test.tsx`、`ai-legacy-compatibility.test.ts`。
- server 全套 16,329 項：失敗 17 項，全部是 zhtw.10 版本說明已列的既有失敗或本機環境因素（`email-channels` ×2 為 worktree 路徑造成、`native-codex-runner` 需要 cargo），新增失敗 0。
- ui 全套 6,740 項：既有「alphabetizes cards」×1；`ChatComposer` ×1 為負載下偶發（單獨重跑通過）；`clipboard-usage` ×1 已在 `10806f024` 修正。
- 兩輪 fresh-context 對抗審查：第一輪「需修」（3 項必修已全部修正），第二輪「可交付」。
- 正式站容器（node 使用者）以白名單環境實測：grok／codex 都能印出並解析授權網址與驗證碼。
