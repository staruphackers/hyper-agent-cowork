# v2026.1019.0-zhtw.12

**類型**：修正版（任務排隊不再斷鏈）　**基於**：v2026.1014.0-zhtw.11　**建版目標**：`main`

## 摘要

同一個任務同一時間只讓一個代理人執行，其他被提及的代理人會排成「等待中」，前一位結束時再叫下一位接手。舊版有一個漏洞：被提及（不是受指派者）的代理人一旦在開始工作後失敗（例如 Grok CLI 回「Not signed in」），系統就停在原地等「人工對帳」，但這種對帳通知只會為受指派者或審查者建立——結果沒有任何人收到通知，排在後面的代理人永遠不會被叫醒。正式站實際有一題因此卡了 6 天。本版讓這條規則只套用在真正擁有這個任務的代理人身上，被提及者失敗時照常把下一位叫起來。

## 變更

### 修正
- **被提及者失敗時照常接力**：釋放執行鎖時的「legacy 對帳」閘門，現在只在「這個 run 的代理人是受指派者，或是待審中的當前審查者」時才停下來等人工對帳；其他代理人的失敗 run 會照常叫醒排隊中的下一筆（每次仍只叫一筆）。
- **判斷條件只有一份**：「誰需要人工對帳」與「誰會收到對帳通知」改用同一個共用判斷（`runOwnsLegacyReconciliation`），兩邊不會再各寫各的而產生落差。

### 行為不變（刻意保留）
- 受指派者或當前審查者的 run 在開始工作後失敗：佇列照舊保留，並建立「需要人工對帳」通知，等你檢查後再繼續。
- 操作者手動停止（已確認的取消）：照舊不自動叫醒後面排隊的人。
- 每次釋放仍只叫醒一筆，順序仍依排隊時間。

## 已知限制
- **卡住偵測沒有一起改**：定期執行的「卡住任務」掃描（`reconcileStrandedAssignedIssues`）仍把任何「等待中」的喚醒當成「還在進行」而略過。本版修掉了造成卡住的來源，但若因其他原因留下沒人持鎖、也沒有任何 run 的等待中喚醒，掃描仍看不到。原因：這個掃描後續的處理全部以受指派者與最新 run 為中心，單純放行並不會把排隊的喚醒叫起來，反而可能走進為受指派者設計的升級或續跑流程；正確做法是另外設計一條「發現孤兒等待中喚醒就接力一次」的專用路徑，列為後續工作。
- 被提及者失敗後，若排在下一位的剛好是同一位代理人的另一筆喚醒，它也會被叫起來（等同重新提及一次）；若該代理人的登入問題沒修，會再失敗一次，但不會再卡住後面的人。

## 升級注意
1. 一般升級：compose 的映像改成 `ghcr.io/staruphackers/hyper-agent-cowork:2026.1019.0-zhtw.12` 後重新建立容器，無資料庫遷移。
2. **已經卡住的任務不會自動恢復**：本版只防止新的卡住，部署前就已經停在「等待中」的喚醒不會被自動處理（卡住偵測沒有一起改，見「已知限制」）。部署後請對每一題卡住的任務**手動叫醒受指派者一次**（在任務頁觸發受指派者，或留一則不提及任何人的留言）；受指派者那一輪結束時就會依排隊順序叫醒下一位，之後一棒接一棒。
3. 手動叫醒前，先確認排隊中代理人的登入都正常（例如 Grok 是否已登入）。登入沒修好的代理人輪到時仍會失敗，但本版起不會再擋住後面的人。
4. **不要**改用重新提及這些代理人來「催」：此時沒有人持有執行鎖，新的提及會立刻各自執行，而舊的等待中喚醒還在，之後會被再叫一次，同一位代理人可能回答同一題兩次。
5. 回滾：映像改回 `2026.1014.0-zhtw.11`。本版沒有資料格式變更。

## 驗證
1. 找一個受指派者正在執行的任務，留言同時提及兩位其他代理人（A、B）。
2. 讓 A 失敗（例如 A 的訂閱未登入）。
3. A 失敗後 B 應自動開始執行；任務不應出現「需要人工對帳」通知（A 不是受指派者）。
4. 對照：讓受指派者自己失敗 → 應出現「需要人工對帳」通知，排隊的人維持等待。
